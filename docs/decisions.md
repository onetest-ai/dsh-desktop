## Managed runtime, final review fix wave (2026-08-22)

Rulings from the last review of `feat/managed-runtime`. The review's structural diagnosis: this branch made Save a six-minute async operation, then reasoned about quit only at the config-write boundary, never at the process or re-entrancy boundaries.

- the update check's `resolveBinary` throws synchronously, so `read`'s `.catch()` never attaches and the throw escapes to `settings:read`. Fixed with a `try` around the call itself, not only around its promise. The renderer's `load()` gains a failure path with Save still enabled: a failed read means the repair screen must stay usable, and disabling Save would take away the only way to fix the config that caused the failure. Cost if wrong: a user who cannot read their config sees defaults with an explanation, and saving replaces rather than edits.
- the npm child moves into `install-process.ts`: detached spawn, tracked from spawn to exit, reaped by `shutdown()` through the same `stopGroup` the harness child uses. Chosen over a second teardown path so quit has exactly one. Cost if wrong: one more module between `index.ts` and `spawn`.
- a killed install must not read as a complete one. `isInstalled` checks the linked binary, but npm links `node_modules/.bin` before the tree is fully written, so the install now runs in a `.partial` staging sibling and is renamed into place only on success. Chosen over a cleanup-on-failure catch, which cannot run when the process is exiting. Cost if wrong: a killed install leaves a `.partial` directory, which the next attempt removes.
- saves are serialized in main with the existing `singleFlight`, not only in the renderer: the reopened-window case proves the renderer is not the only entry point. A second caller joins the run in flight and receives its outcome rather than starting a second install. Cost if wrong: a save submitted during another save silently adopts the first one's form; the window shows the result and the user can save again.
- progress and update-available are pushed to the `WebContents` that invoked the channel, rather than making a reopened window reflect the in-flight install. The narrower fix: a reopened window showing an idle Save is honest about itself, and would be actively misleading if it also streamed another window's output. Cost if wrong: a user who reopens Settings mid-install sees no progress until it finishes.
- `npm view` is bounded at 60s and `npm install` at 900s. The install bound is roughly 2.4x the measured 375s cold install, which leaves room for a slow network without letting a hung registry disable Save forever; the lookup bound is far below it because it is one request for one field on the path that opens Settings. Cost if wrong: a genuinely slower-than-2.4x cold install fails with a timeout the user can retry.

## MCP servers tab (2026-08-25)

Rulings from adding the MCP tab, its preset catalog, and its secret store.

- MCP is its own `desktop.json` section, not plugin entries. One package (`@deepseek-ai/dsh-mcp-client`) backs every server, and the plugin list is one entry per package — `parsePluginsField` rejects duplicates and `insertId` derives the row id from the package name, so two servers could not coexist there. Cost if wrong: a second config section to keep in step with the first, rather than one list.
- Servers reach the overlay through `patchOverlay`'s existing `declaredPatch` path rather than a new one. That path already emits several rows with author-chosen ids and already serializes through the `!!js`-aware schema — both of which MCP needs and the synthesized-row path provides neither of. `runtime-files.ts` is unchanged as a result. Cost if wrong: MCP rows are shaped by a mechanism built for a different purpose, so a future change to declared patches has a second consumer to consider.
- The token is named in the overlay by `!!js process.env.…` and passed through the harness child's environment, never written into the generated file. The overlay is rewritten every boot into a plain file; a credential there would be the single worst place to put one. Cost if wrong: a user reading the overlay sees a variable name instead of a value and has to know where the value comes from — which `docs/notes/mcp-servers.md` states.
- No `?? ''` guard in the `Bearer` expression. `serverEnv` defines a variable for every server a row is emitted for, empty when no token is stored, and the two are generated together for the same boot — so the guard is unreachable, and dropping it also stops js-yaml from quote-escaping the scalar. Cost if wrong: an overlay generated without its matching environment yields the header `Bearer undefined` rather than an empty bearer; nothing generates one that way today.
- `safeStorage` directly, with no platform-selection layer over it. It already selects Keychain / DPAPI / libsecret per platform, which is exactly what a hand-written abstraction would have to reproduce, worse. The seam is one module (`secrets.ts`) so the mechanism stays swappable and testable, not a framework. Cost if wrong: swapping the store later touches one file.
- A Linux desktop with no keyring gets a refusal, not a plaintext fallback. `isEncryptionAvailable()` false means the backend is `basic_text`, which is not encryption; writing there would put a credential in a file whose name claims otherwise. The `DSH_MCP_TOKEN_*` environment variable is the documented way out, since that is where the token ends up regardless. Cost if wrong: a user on such a machine cannot save a token from the UI and has to set an environment variable.
- Linear and Atlassian ship in the catalog listed and disabled, rather than being omitted. Each was probed directly and answers an unauthenticated `initialize` with `WWW-Authenticate: Bearer realm="OAuth"` and no other scheme, so a token field for them would be a dead end found only after pasting something; omitting them would leave a user unsure the app knows the name at all. Cost if wrong: two rows in the picker that cannot be selected yet.
- Tokens are write-only from the renderer: `read` reports presence, never value. Cost if wrong: a user who forgot a token must paste a new one rather than reading the old one back — which is the intended property.
- `validateSettings` omits the `mcp` section entirely when the tab is off with nothing configured, so a user who never opens it keeps a `desktop.json` with no trace of the feature. This also kept three existing exact-object save assertions passing unchanged rather than churning them. Cost if wrong: none; the field is optional and `formFor` already defaults it.
- The renderer's MCP code uses single-argument `append` and no text nodes, matching the rest of `settings.js`. The first draft used both and rendered nothing under the spec's fake DOM — the failure was in the test double, but the idiom it enforces is the file's own. Cost if wrong: slightly more verbose row construction.
- No live GUI verification was possible in the session that built this: the app exits immediately under a fresh `$DSH_HOME` in that environment, and does so identically on the unmodified baseline, so it is a property of the environment rather than of this change. Coverage is the 578 unit tests, including the boot-path integration cases in `index.spec.ts` and mutation checks on the secret store and the environment plumbing. Cost if wrong: a defect living purely in the packaged preload/IPC wiring for the two new channels would still reach the user.
- the MCP client is refused by the Plugins tab's Add control, filtered out of the list it shows, dropped from `plugins` on save, and skipped at boot. Found live: a stored bare entry for it carries no config, cordis rejects that at load, and the row sat in Settings offering a Config editor for something the MCP tab owns. Four places rather than one because the entry can arrive by hand edit or predate the tab, and each layer answers a different moment — adding, showing, persisting, booting. Cost if wrong: a user who deliberately wanted to hand-configure that package as a plugin cannot; the MCP tab is the supported path.
- adding the first server turns the master switch on. Found live: the shipped build let a user add Tavily, save a token, and get silence — `"enabled": false` with an individually-enabled server means `activeServers` is empty, so nothing installs and no row reaches the overlay. Adding a server is an unambiguous statement of intent. Only the FIRST add flips it, so a deliberate switch-off with servers already listed is not overridden. Cost if wrong: a user who wanted to stage a server without connecting it has to untick the box.
- servers-configured-with-the-feature-off also gets a standing warning, not just the auto-enable. The auto-enable does not cover the state arriving from a hand-edited `desktop.json` or from a user unticking the box, and that state is the one where the tab looks fully configured and does nothing. Toned `--setup`, not `--danger`: nothing is broken, a step is missing. Cost if wrong: one more line on the tab in a state that should be rare.
- the `<select>` is fully reset and rebuilt on `input[type='text']`'s metrics with an inline-SVG chevron. The native control paints a light-mode-only well and ignores every theme variable, which read as a foreign element in dark mode. The arrow is a background image because `select` cannot carry `::after` and a wrapper would sit between the row's flex children and their sizing. Cost if wrong: the picker no longer looks like the platform's own control, which is the point.
- `index.spec.ts`'s MCP suite takes a temp `$DSH_HOME` per case. Without one it read the developer's real `~/.dsh` and decrypted an actual saved token with the fake test key — a machine-dependent test that passed only on a machine with no tokens saved. Cost if wrong: none.

## Signing and distribution (2026-08-25)

- the real defect was not the missing notarization but an invalid signature. `identity: null` made electron-builder skip signing, leaving Electron's linker-signed stub with `Sealed Resources=none`, which `codesign --verify` rejects. Measured under simulated quarantine: an invalid seal yields "is damaged and can't be opened" with **no** override offered, while a valid ad-hoc seal yields "Apple could not verify…" with Open Anyway. Cost if wrong: none; the ad-hoc path is strictly better than the stub it replaced.
- ad-hoc signing is a fallback, not a policy. `build/adhoc-sign.js` skips when a real identity already signed the bundle, and decides that by READING the signature rather than checking `CSC_*` env vars — keychain auto-discovery sets neither, so an env-only guard would overwrite a Developer ID signature with an ad-hoc one and produce an artifact Apple refuses to notarize. Caught before it shipped. Cost if wrong: an unsigned build gets signed twice, which is harmless.
- `mac.identity` is removed from `package.json` rather than set to `null`: absent means auto-discover, `null` means force-skip. Cost if wrong: a machine with an unrelated Developer ID cert signs with it unexpectedly, which `security find-identity` makes visible.
- notarization is enabled on `npm run release` only, not in `build.mac.notarize`. Enabling it in config would fail every ordinary `dist` on a machine without credentials. Cost if wrong: someone runs `dist` expecting a notarized artifact and gets an ad-hoc one; `spctl` says which.
- `dir` target kept alongside `dmg` because `tests/smoke.spec.ts` runs against `release/mac-arm64/<app>.app`. Cost if wrong: one redundant output directory per build.
- hardened runtime (`--options runtime`) is applied to the ad-hoc signature too, not only to Developer ID builds, so the entitlements are exercised in ordinary local builds rather than first engaging on release day. Verified the app still launches under it (smoke passes). Cost if wrong: a hardened-runtime problem surfaces locally instead of during a release, which is the intent.
- the README's "right-click and choose Open" instruction was stale — Apple removed that bypass in macOS 15, and this machine runs 26.5.2. Corrected to the System Settings path plus the `xattr` one-liner. Cost if wrong: none; the old advice did not work.

## MCP token storage (2026-08-25)

- tokens move from Electron's `safeStorage` to **cleartext** in `$DSH_HOME/desktop-secrets.json`, mode `0600`. A Keychain item's ACL trusts specific signed binaries, so every re-signed build, bundle-id change, and separate copy of the app raises its own login-password prompt — several scary dialogs before an ordinary user gets the app working. Diagnosed on this machine: today's work alone changed the signature three times (broken ad-hoc, valid ad-hoc, Developer ID) and the bundle id once, which is what produced the repeated prompts; stable signing would reduce it to one. The decision stands anyway: matching `.mcp.json`, `~/.aws/credentials`, `~/.npmrc`, and `gh` is the norm for developer tools, and this app's agent already runs shell commands as the user. Cost if wrong: any process running as this user can read the tokens, and they land in backups. `secrets.ts` remains the single seam, so reverting is one file.
- the document is versioned. The old format stored base64 ciphertext under the same `{id: string}` shape, so the two cannot be told apart by inspection, and a leftover ciphertext read as a token would be sent to a server as a bearer credential. An unversioned document is discarded, not guessed at. Cost if wrong: anyone upgrading re-enters their tokens once.
- saving a token shows "Saving, and restarting the agent…" for the duration. Measured in the packaged app: the write is instant but `setMcpToken` does not resolve until the harness respawns, about 17 seconds, during which the row previously showed its old text behind a disabled button. Cost if wrong: none.

Requested explicitly; the first answer given was to keep them hardcoded, on the reasoning that a bundled JSON would need its own copy step and could go missing with no compile error. That reasoning was wrong on the first count: `assets/**/*` is already in `build.files` and verified inside `app.asar`, so the file ships with no build change at all. The second count is real and is answered by a smoke-test assertion rather than by avoiding the format. Cost if wrong: the catalog is no longer type-checked, so a malformed entry is caught by a test rather than by the compiler.
- the user overlay is what makes the catalog updatable without an app release — correcting an endpoint, or handing a team its own internal servers. Cost if wrong: a user can add a preset naming a command to run, which is exactly the trust `mcp.json` already carries for the same user.
- a REMOTE catalog stays out of scope. A preset names a command; fetching that over the network would give whoever controls the URL arbitrary code execution on every machine at app start. It would need signed payloads and pinned keys to be responsible, which is a project rather than a file format. Cost if wrong: updating the shipped catalog needs a release, and the user overlay covers the urgent cases.
