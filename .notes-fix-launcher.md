# Fix: eager launcher resolution vetoing startup, and configuration failures opening Settings

## Finding 1 — eager `Launchers` resolution

**Root cause.** `dshWebCommand` (`src/main/server.ts`) built a `Launchers` struct by
calling `resolveBinary` for both `pnpm` and `npx` before `spawnFor` picked a
branch. `resolveBinary` throws under a Finder-minimal `PATH` when the binary
has no configured path. So local mode with a valid `pnpmPath` still threw on
the unrelated, unconfigured `npxPath` — the exact reported symptom.

**Fix chosen: lazy resolver thunks, not eager strings.**

`Launchers` (`src/main/harness-source.ts`) is now:

```ts
export interface Launchers {
  pnpm(): string
  npx(): string
}
```

`dshWebCommand` passes closures — `() => resolveBinary(config.pnpmPath, 'pnpm', process.env)`
and the `npx` mirror — instead of resolved strings. `spawnFor` is unchanged in
structure: it still branches on `source.kind` and returns a `SpawnSpec`, but
now calls `launchers.pnpm()` or `launchers.npx()` only inside the branch that
needs it. This was chosen over moving `resolveBinary` calls directly into
`spawnFor`'s branches because `spawnFor` already owns a `HarnessSource →
SpawnSpec` mapping and has no reason to know about `resolveBinary`,
`DesktopConfig`, or `process.env` — the resolution rule stays fully in
`resolveBinary`, invoked from one call site (`dshWebCommand`), and `spawnFor`
stays a pure mapping that merely decides *which* resolver to call, never
*how* to resolve. The only change to `spawnFor`'s shape is that `Launchers`
carries thunks instead of values.

`resolveBinary`'s behavior and error message are untouched; it now throws a
`ConfigurationError` (see Finding 2) instead of a plain `Error`, same message.

## Finding 2 — configuration failures open Settings

Added `src/main/configuration-error.ts`: a `ConfigurationError` class marking
a startup failure the user can fix in `desktop.json` — unresolvable launcher,
missing/invalid config, missing/unbuilt checkout — as opposed to a correctly
configured harness that crashed or timed out after actually launching.

- `resolveBinary` (`server.ts`) throws `ConfigurationError`.
- `config.ts`'s `loadConfig`/`parseConfig` throw `ConfigurationError` for an
  unreadable, malformed, or invalid `desktop.json`.
- `preflight`'s `{ ok: false }` result is inherently configuration-class (a
  missing/unbuilt checkout); no exception type needed there since it never
  throws.
- `index.ts` adds `failConfiguration(title, detail)` = `fail(...)` +
  `showSettings()`, used for: the `loadConfig` catch in `bootNow`, the
  `preflight` failure branch, the top-level `whenReady` config-load catch
  (previously called `fail` + `showSettings` inline; now shares the helper),
  and — the one place needing runtime discrimination — the `startServer`
  catch block in `bootNow`, which now branches on
  `error instanceof ConfigurationError` to call `failConfiguration` only for
  a launcher-resolution failure, and plain `fail` for every other rejection
  (readiness timeout, early exit, spawn ENOENT).
- `writeRuntimeFiles` failures are deliberately left as plain `fail` — not
  one of the three named configuration classes, and not something Settings
  fixes.

Settings remains reachable from the menu/tray in every case regardless
(unchanged, pre-existing).

## Verification against the real packaged app

`~/.dsh/desktop.json` on this machine is local mode with a valid `pnpmPath`
and no `npxPath` — the exact reported configuration.

Ran `npm run pack`, then launched the packaged app with a deliberately
minimal environment:

```
env -i HOME="$HOME" PATH=/usr/bin:/bin:/usr/sbin:/sbin:/Users/.../nvm/.../bin \
  "release/mac-arm64/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness" > log 2>&1 &
```

(The nvm `bin` directory was added only because this machine's `pnpm` is a
Corepack shim script with a `#!/usr/bin/env node` shebang — an OS-level
detail of how the *configured* `pnpmPath` binary is itself executed, entirely
unrelated to `resolveBinary`'s own PATH-scanning logic, which only runs when
no `pnpmPath`/`npxPath` is configured. Homebrew/Corepack shim directories
that would let a *bare* `pnpm`/`npx` resolve were never added — that's the
condition under test.)

The app's own stdout stayed empty (the main process never `console.log`s the
ready URL — it only parses its child's stdout internally), so readiness was
confirmed by process-tree and network evidence instead:

- Process tree spawned correctly under the packaged app's PID: `pnpm dsh
  --profile web --patch ... --no-open` → `node --import tsx/esm
  apps/cli/src/bin.ts ...` → an `esbuild` grandchild — proving `pnpmPath`
  alone (no `npxPath`) was sufficient to launch, with no veto from npx
  resolution.
- `lsof` showed the harness child listening on `127.0.0.1:<port>` (an
  OS-assigned port, e.g. `59274`).
- `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:<port>/` returned
  `200`, and the body was the harness Web UI's `<!doctype html>` shell —
  i.e., the app reached a real `127.0.0.1` URL and served the UI, not the
  reported npx error.
- Quitting via `kill <captured PID>` reaped the entire process tree
  (packaged app, `pnpm`, `dsh` CLI, node-pty grandchild) — no orphans left
  behind, confirmed by `ps` showing nothing for any of the captured PIDs a
  few seconds later.
